# Beyond Passing Tests: Creator Judgment in Agentic UI Development

My position is that good agentic UI development depends on creators who define an intended experience, question the agent's framing, and revise their judgments through evidence. Automated checks and user feedback support that responsibility; neither supplies the project's purpose. In Card Clash, I wanted players to feel that they were holding cards at a shared war table. Passing gameplay tests could protect rules without establishing that experience. The broader challenge is deciding which qualities to formalise and when an apparently successful implementation needs reconsideration.

Barr et al. (2015) frame the test oracle problem as deciding whether observed behaviour is correct. Their survey considers specifications, contracts and other automated approaches alongside human knowledge of informal expectations. This helps explain the gap without dismissing tests: a passing suite answers the questions encoded in its oracles. My inference is that agentic workflows need explicit responsibility for choosing those questions. If the agent implements and checks only its current interpretation, repeated correction can leave the interpretation itself unchallenged.

Visual evaluation can also be automated. Design2Code combines screenshot-based metrics with human evaluation when assessing generated webpages (Si et al., 2025). This moves evaluation closer to rendered outcomes than source-code similarity does. Its reported disagreements between automatic and human rankings also caution against relying on a single measure. Reproducing a reference screenshot and creating an understandable interaction are different objectives. I infer that strong visual similarity cannot by itself establish whether players understand targeting or recognise a usable control. The creator still has to justify the evaluation target, rather than treating a benchmark score as a complete definition of quality.

My [project record](PROCESS.md) illustrates this distinction. Repeated UI revisions coexisted with passing checks while my inspection found weak spatial relationships, obscured cards and an unconvincing first-person composition. I specified normal desktop play with four to six cards as the main visual case, preserved gameplay constraints, and redirected work toward a root-cause audit. Claude Code was followed by Codex, but the instructions, inspection and acceptance criteria also changed. This sequence cannot establish one model's superiority. My contribution was deciding when local repairs were no longer addressing the intended experience; the project is an illustrative case, not a controlled experiment.

The counterargument is that apparent dependence on human judgment may simply reveal inadequate automation. Walsh, Kapfhammer and McMinn (2017) demonstrate automated detection of responsive layout inconsistencies without an explicit reference oracle. Their work challenges any claim that visual defects inherently require manual review. Playwright's visual-comparison documentation likewise describes repeatable screenshot checks, while warning that rendering environments affect results (Microsoft, n.d.). Yet a stable screenshot baseline can preserve an unsatisfactory design. My conclusion is therefore to expand automation where claims become precise, while retaining responsibility for questioning the baseline and deciding whether consistency serves the intended experience.

Creators' preferences also need scrutiny. Two classmates independently using [Card Clash](docs/card-clash-playtest.md) reported interaction defects despite liking the artwork. I directed repairs to targetless-card dropping and excessive discarding, with constraints added to the harness and tests. Their follow-up confirmed those fixes but raised a new Lobby-button concern. This feedback challenged my judgment rather than originating the design. Two brief sessions cannot establish general usability, and retained server actions cannot establish how an interaction felt. Keeping these limits visible makes creator responsibility accountable rather than absolute.

I therefore propose a practical division of work: creators articulate and revisit experiential goals; agents implement bounded changes; automated checks protect explicit properties; browser inspection and independent use challenge what those checks miss. Stable discoveries should become specifications or regression checks where practical. The creator's role is not continuous manual correction of everything the agent produces. It is deciding what merits correction, recognising when the problem has been framed poorly, and explaining how evidence changed that decision. Better automation should strengthen this judgment, not obscure who remains responsible for it.
